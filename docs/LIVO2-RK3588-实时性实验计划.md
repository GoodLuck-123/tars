# FAST-LIVO2 在 RK3588 上的 15 Hz 实时性实验计划

## 目标和边界

本实验在独立 Git 分支 `codex/livo2-rk3588-realtime` 上进行，保护 `tars/main` 这个数据采集主干。工程目录、采集 CLI、远端板端环境和原始传感器数据流程保持独立；只有经过单项测量、可复现且没有明显回归的算法优化，才以小模块提交并选择性合入本实验分支。不会把探索期的性能参数、灰度图链路或算法补丁直接带回采集主干。

目标是让当前 RK3588S（ROC-RK3588s-PC 定制板）在无人机挂载场景的初始约束下，用现有 Livox AVIA、FLIR 彩色相机和 AVIA 内置 IMU，达到 **15 Hz 的可持续 LIVO 更新能力**。15 Hz 的验收预算是单帧 66.7 ms；验收暂不要求传感器固联、硬触发、飞行状态、轨迹精度或地图精度达标，但必须保留这些条件未验证的记录。灰度图可以作为性能实验输入，不能默认代表最终彩色传感器配置。

## 实验形态和顺序

### 0. 分支、仪器和安全基线

- 从当前可运行版本创建本分支；每次实验记录 Git 提交、子模块提交、运行包指纹、板端 CPU 频率/温度、内存峰值、输入频率、处理频率、积压和退出状态。
- 所有输出写入被忽略的 `results/` 或 `.cache/`，只向 `evidence/performance/` 保存小型 JSON、摘要和图表数据。
- 加一个性能记录入口或复用现有 supervisor，不改变 `tars/main`；测量“算法处理时间”“ROS/输入等待”“排空尾部”和“保存时间”，不能只看整段墙钟。
- 每个变更前先跑同一段数据集基线，若基线本身漂移则暂停优化，先查板端调频、温度、输入时间戳和数据完整性。

### 1. 数据集基线：先证明在板上能稳定跑

- 使用现有 AVIA 数据集和当前相机配置，先在主机确认消息类型、时间戳、图像尺寸、有效点比例和相机帧率。
- 在 RK3588 上用固定起点、固定时长和固定回放速率复现原版 FAST-LIVO2；关闭 RViz 和不必要的可视化，保留完整日志。
- 记录每个视觉更新的端到端延迟、LIO/VIO 分项耗时、处理频率、积压量、A55/A76 利用率、峰值内存和温度。基线结果先形成一份可比较的报告，再决定优化顺序。
- 通过标准是：轨迹/地图输出完整、没有输入丢失或时间戳回退、任务正常收尾；实时性结论分为“15 Hz 处理达标”“15 Hz 输入不积压”“仅完整序列墙钟达标”，不能混为一谈。

### 2. 低风险输入优化：先做图像和传输路径

按“一项改动、一份对照、一条提交”的方式尝试：

1. **灰度图模块**：在现有相机/回放链路旁增加明确的 `color -> mono8` 适配，保证时间戳、CameraInfo、曝光元数据和队列语义不变；FAST-LIVO2 本身要求灰度图。先验证它是否只是消除重复转换，不能先假定一定提速。
2. **工作分辨率对照**：比较完整幅面、当前 640×512 工作尺寸和更小尺寸。同步缩放内参，保存像素重采样说明；精度暂不验收，但必须记录图像处理耗时和视觉更新数。
3. **输入格式和队列**：比较 raw、压缩解码和有界队列；观察丢帧、延迟和算法是否处理旧图。实时系统优先保持新鲜数据，不能用无限队列隐藏积压。
4. **视觉帧选择**：如果处理时间仍超过预算，增加显式的“最多每 N 个图像帧进入视觉更新”实验开关，保留全部传感器原始输入；先验证 LIO 连续性和视觉更新节奏，再决定是否进入默认配置。

每项都要能独立回退，不能把灰度、降分辨率、跳帧同时提交后再猜原因。

### 3. 调度和编译优化：在不改估计模型的情况下压缩尾延迟

- 验证 A76 CPU 绑定、OpenMP 工作线程数、OpenCV 线程数、`performance` 调频和被动等待策略的组合；单独记录温度和频率，避免把短时升频误称为长期实时。
- 检查 Release/O3、NEON、Eigen/OpenMP、链接库和 ARM64 运行包是否确实生效；比较板端原生编译与主机交叉编译产物，禁止把 `-march=native` 的 x86 产物误放到板端。
- 处理 ROS callback、锁竞争、内存分配和复制；优先使用已有代码路径和小型适配，不引入第二套 ROS 或全新通信框架。
- 对每种组合保留 CPU、RSS、频率、温度、输入积压和更新频率，选择稳定的最小收益组合，而不是只挑最好的一次运行。

### 4. FAST-LIVO2 参数和地图开销优化

先做配置开关和短段对照，再考虑源码修改。顺序建议为：

- 暂停 PCD/图像保存和不需要的发布；确认保存开销不进入实时预算。
- 逐项比较 `dense_map_en`、raycast、地图层数/体素大小、点数上限、视觉和 LIO 最大迭代次数、patch 金字塔层数及点云过滤密度。
- 保留 `accuracy_mode` 与 `realtime_mode` 两组明确配置，所有降低计算量的选项有名称、有默认值、有证据，不能把实验参数散落到上游 YAML。
- 15 Hz 的最低通过条件是有效输入不长期积压、视觉更新不被完全关闭、LIO/IMU 连续；精度、漂移、地图完整度另开评估，不用“能跑”代替精度结论。

### 5. 真实传感器接入和现场实时性

- 数据集达到候选 15 Hz 后，接入真实 AVIA、FLIR 和内置 IMU；先静态/手持，再考虑无人机安装。传感器未固联时只测吞吐、延迟和稳定性，不做位姿精度结论。
- 先用软件统一时间戳和当前无硬触发链路验证数据流；硬触发、相机—雷达—IMU 时延和外参放到后续硬件固定阶段。
- 实采验收要包含：三路频率、丢帧/丢包、时间戳单调性、端到端延迟、处理积压、温度、内存、持续时间和正常停止恢复。主机网线拔除后板端任务应继续，重连后按现有 `status/stop/pull` 回收。
- 真实传感器达到同样的 15 Hz 预算后，再做代表性手持/无人机静态场景；若数据集达标而真机不达标，优先定位驱动、USB、网络、时间戳和图像曝光链路，不直接改算法。

### 6. 候选上游方案和社区结果

- FAST-LIVO2 原论文描述了 ESIKF、顺序更新、直接图像/雷达融合、统一体素地图和按需 raycast；这些是理解瓶颈的基线，不等于当前 RK3588 已达标。
- 作者团队的资源受限平台论文报告了面向 ARM/RK3588 的自适应视觉帧选择和内存高效地图，原版在论文配方中的单帧总耗时约 75.87 ms，轻量改进版本约 37 ms。这里的改进应作为独立实验方向，先确认代码、许可证、数据和传感器接口，再决定移植；不能直接把论文数字写成本工程结果。
- 可参考社区的 RK3588 FAST-LIVO2 适配，但必须检查其传感器型号、消息类型、共享内存接口、校准和 CPU 配方；外部配置不直接覆盖本工程配置。任何上游移植都先做独立适配提交。

## 提交和合入规则

- 分支只允许使用语义明确的小提交，例如：`perf: add grayscale input adapter`、`perf: bound visual queue`、`perf: tune RK3588 worker affinity`、`perf: add realtime preset`。
- 每个提交必须附带：基线 run-id、优化 run-id、输入数据指纹、运行包指纹、关键指标和回退方法；未达到预期的实验保留在本分支但不合入采集主干。
- 只有在同一条件重复运行仍正向、没有输入完整性回归、没有明显精度/稳定性风险时，才合入 `codex/livo2-rk3588-realtime` 的算法线；`tars/main` 永远不直接合入这些探索提交。
- 本计划完成后先做基线，不把计划本身当作实时性结论。

## 当前已知起点

此前工程证据显示：RK3588 上原版 FAST-LIVO2 完整序列约 14.8 Hz，LIO+VIO 平均约 82.18 ms，仍高于 15 Hz 的 66.7 ms 单帧预算；论文中约 37 ms 的数字属于资源受限改进版本，不能替代本工程测量。当前需要从同一数据集、同一配置重新复测，确认版本差异后再开始优化。
