# RK3588 性能核查（2026-10-23）

用户提出原版应能在 RK3588 运行后，重新检索作者资料，并在同一块板上做对照；旧版功能验收的 528 秒不能代表硬件极限。

## 公开证据

- [FAST-LIVO2 作者在 Issue 67 的回复](https://github.com/hku-mars/FAST-LIVO2/issues/67)：明确认为 RK3588 足够，说明算法最多四个计算线程，提问中的高占用主要来自 RViz。本工程未启动 RViz，因此不能照搬该问题的原因。
- [作者团队资源受限平台论文，第 V-A3、表 II、第 V-C2 节](https://arxiv.org/html/2501.13876v1)：ARM 平台是 RK3588，表 II 的原版 FAST-LIVO2 合计 75.87 ms（雷达 56.50、视觉 19.36）；37 ms 的实测属于论文提出的轻量改进算法，不能当作本工程原版的结果。论文使用的数据、频率和配方与本地不同，不能据此保证任意参数实时。

## 本地发现与修改

实际设备树为 Rockchip RK3588S LP4X LIXU Board；4 个 A55（CPU 0–3，最高 1.8 GHz）和 4 个 A76（CPU 4–7，最高 2.352 GHz）。原调频器为 interactive，负载采样中部分 A76 仍降至 408–1008 MHz；算法 OpenMP 工作线程还多次运行在 A55。

原构建已启用 Release、O3、OpenMP 四线程、ARM NEON；不是误用了 Debug。ARMv8-A 指令集可运行，暂无证据把慢速主要归因于通用架构编译选项。

保持点云过滤、ICP、视觉迭代参数不变，依次测量：A76 绑定 + OpenMP 被动等待、performance 调频、OpenCV 单线程。生产配置将这些集中在 project.yaml 的 runtime；performance 只在任务期间启用，正常完成、主动 stop 和受控异常均恢复原调频器。需要板端 sudo -n；cpu_governor: null 可关闭调频。主机断线时板端任务继续，任务结束后恢复；直接 SIGKILL/断电无法执行 finally，重新使用前应检查调频器。

原图像链路在 1280×1024 完整解码、去畸变和 ROS 传输后，算法再缩成 640×512。现由解码器直接输出配置的工作尺寸，0.5 缩放时使用 JPEG 半尺寸解码，完整保留五参数畸变模型，内参同步缩放，下游 scale=1，避免重复缩放。此修改改变重采样像素值，不能宣称与旧图像逐像素等价；未进行真值精度评测。

所有对照均使用 /home/eric/data/hku_campus_seq_03.bag；30 秒短段采用相同起点。改变回放速率的对照必须同时比较逐帧时间与积压，不能只用整个任务墙钟（含输入等待、排空、保存）。原始配置、日志、结果和 SHA 清单保留在 results/<run-id>。

同一条带 [ Data Cut ] 标签的 ERROR 曾被两个 ROS 日志格式重复计数，已修正只剥离 ROS 元数据；真实的启动期旧图像丢弃和退出时 XMLRPC 错误继续保留。

30 秒逐项对照见 runs.json：原包原调度 93.04 s，A76 绑定/被动等待后 71.19 s；同一旧图像链路、OpenCV1、1 倍输入时，interactive 与 performance 分别为 68.21 s 和 46.28 s。缩放解码同条件为 47.33 s，未改善主要由 ICP 决定的短段墙钟，但将解码 CPU 从 27.17 s 降至 11.71 s。不把它包装成主要计算瓶颈的修复。

完整段更新约 14.8 Hz，LIO+VIO 平均 82.18 ms，已超过约 67 ms 的更新预算，另有回调、IMU、保存开销。论文中 37 ms 属于另一种算法，论文的 10 Hz 演示也不能替代此处的 15 Hz 条件。后续实时目标应单独控制输入频率、点云密度和精度评测；本轮没有减少点云、跳过视觉或降低迭代次数来制造达标结果。

两次完整结果时间戳逐项一致；相对旧版估计轨迹的位置直差均值 1.58 cm、最大 4.75 cm，仅用于排查明显回归，不能当作真值误差。图像重采样和并行计算均有差别，精度仍需独立验证。

cpu-samples.json 记录前 50 秒两组 A76 恒为 2.352 GHz；后半段独立读取仍为该频率，最高温度约 73°C。本次没有观测到降频，但这不是长期热稳定性验收。原 interactive 调频器已在结束后恢复。
